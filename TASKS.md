add a date/note) as it moves, rather than waiting until the whole milestone

`done` / `blocked` (cannot be advanced by the coding agent regardless of
effort — needs the user, e.g. an external account signup).

## M1 — Universe module

Broadened mid-milestone from S&P 500-only to the full S&P Composite 1500
(S&P 500 + S&P 400 MidCap + S&P 600 SmallCap) per user decision 2026-07-21
— see DESIGN.md §3.1.

**Sourcing history (all resolved 2026-07-21):** three alternatives to a
pure Wikipedia scrape were evaluated for the S&P 500 leg and rejected,
in order: (1) ETF-issuer holdings files (SLY 404s, SPY's Sector column
blank); (2) Finnhub (no S&P 400/600 constituents endpoint at any price);
(3) Financial Modeling Prep's `sp500_constituent` REST API — initially
adopted as a hybrid (FMP for 500, Wikipedia for 400/600, since the user
acts on this system's output with real money and API sourcing looked
like the more reliable option for the largest slice), fully implemented
and reviewed, but then found **live** to require a paid plan: the
legacy endpoint (`/api/v3/`) was sunset 2025-08-31 (`HTTP 403`), and the
current endpoint (`/stable/sp500-constituent`) returned `HTTP 402`
("Restricted Endpoint... upgrade your plan") even with a real, valid key.
User declined to pay for FMP's Starter plan (~$19/mo) — **reverted to a
uniform Wikipedia scrape for all three indices**, the same hardening
(per-index validate-and-fallback, dedup, alert-severity tiering) applied
throughout, just without a second source technology to reconcile.

**Fallback is per-index, not all-or-nothing** (DESIGN.md §3.1): each of
the three indices is fetched/validated/falls-back independently, so the
static fallback file needs a source-index column to slice from, and each
per-index fallback gets its own alert (DESIGN.md §3.6) rather than
relying on the aggregate ticker count, which would still look healthy.
Combined results are de-duplicated by ticker (500 → 400 → 600 precedence
on conflict) to handle the rare index-reclassification window where a
ticker briefly appears in two source lists at once — confirmed live: a
real ticker (BTSG) currently appears on both the S&P 400 and 600
Wikipedia pages.

| **New, this milestone — GitHub Actions persistence for `state.json`/`journal.db` across ephemeral runners** | done, **verification pending** | 2026-07-22 — GitHub Actions runners are ephemeral; without this, every scheduled run would silently reset the two-strike counters and the append-only journal to empty, breaking reconciliation and the sell discipline without any error. Staff-engineer-reviewer confirmed the git mechanics themselves (orphan-branch bootstrap, `--allow-empty` commit, `set -e`-safe `[ -f ] &&` idioms) are sound; `permissions: contents: write` should be sufficient for the default `GITHUB_TOKEN` to push, **assuming no repo-level branch-protection ruleset blocks direct pushes** — worth a one-time manual check against the real repo settings, not inferable from the YAML alone. **This entire mechanism is unverified against real GitHub Actions as of this writing** — it cannot be tested locally; verify via `workflow_dispatch` (2+ manual runs, confirming the second one actually restores what the first left behind) before trusting the quarterly cron with it. **Blocked on tooling, not just time**: the coding agent's environment doesn't have the `gh` CLI installed, so it can't dispatch or inspect these runs itself (and won't work around that by scanning the environment for credentials) — this verification needs the user to trigger `workflow_dispatch` via GitHub's web UI (Actions tab, both `quarterly-run.yml` and `heartbeat.yml`) at least twice each, or to set up `gh` CLI access for the agent. |
| **New, this milestone (pm-reviewer finding) — GitHub auto-disables scheduled workflows after 60 days of repo inactivity** | done, **verification pending** | 2026-07-22 — this project's ~91-day quarterly cadence is longer than GitHub's 60-day auto-disable window; if the only repo activity between quarters were the `bot-state` branch commit (once every ~91 days, itself past that window), `quarterly-run.yml`'s schedule could silently deactivate with no alert. This is also, independently, the "total scheduler failure" gap the data-freshness row above explicitly couldn't close (nothing inside `bot.py` can observe the scheduler never firing at all). Fixed with a second, monthly workflow, `.github/workflows/heartbeat.yml`, which independently checks `quarterly-run.yml`'s own GitHub Actions run history via `gh run list` — if the last recorded run is >130 days old, it fails (same GH-failure-email channel as everything else). **Verified GitHub's actual policy before relying on it (pm-reviewer caught this)**: GitHub's docs state only "scheduled workflows are automatically disabled when no repository activity has occurred in 60 days" — they do not specify whether a scheduled workflow merely *executing* counts as activity, and neither does the community discussion checked; this is genuinely as ambiguous as M8's `notional`-on-limit-order documentation conflict. Rather than gamble on an unverified reading, `heartbeat.yml` now actually pushes a commit every month (to a dedicated `heartbeat` branch, not `main`, to avoid mixing automated noise into the human-curated history or hitting a branch-protection rule more likely to apply to `main` specifically) — an unambiguous git push counts as "activity" under any reading of the policy. **Also unverified against real GitHub Actions** — verify alongside the `bot-state` persistence mechanism above. |
